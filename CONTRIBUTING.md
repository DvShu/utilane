# Contributing and releasing

English | [简体中文](CONTRIBUTING.zh-CN.md)

## Setup and validation

Recommended: Node.js 22.18+ or newer and pnpm, using the committed pnpm-lock.yaml.

```sh
pnpm install --frozen-lockfile
pnpm lint
pnpm format:check
pnpm typecheck
pnpm test
pnpm docs:check
```

Test builds first, then runs Node tests. Docs:check builds JavaScript and .d.ts files, then checks local file links, English/Chinese page pairs, and the types of standalone ts examples. It never rewrites Markdown. Examples are checked separately and must import their own APIs. This does not execute examples, compare API reference signatures with source, prove translation accuracy, or check remote URLs or Markdown anchors.

## Linting and formatting

Use Oxlint for source, scripts, tests, and the build config, and Oxfmt for supported repository files. Configuration: .oxlintrc.json and .oxfmtrc.json. Correctness diagnostics and unused variables are errors; warnings also fail lint. Prefix intentionally unused bindings with an underscore or omit unused catch parameters.

```sh
pnpm lint
pnpm lint:fix
pnpm format
pnpm format:check
```

Lint:fix applies safe fixes; review the result. Format writes changes; format:check only reports differences. Use two spaces, double quotes, semicolons, trailing commas, and LF. Preserve Markdown prose wrapping and do not reformat embedded examples. Exclude lib, node_modules, archives, and pnpm-lock.yaml from formatting. These tools are development dependencies. See the [Oxlint configuration](https://oxc.rs/docs/guide/usage/linter/config) and [Oxfmt configuration](https://oxc.rs/docs/guide/usage/formatter/config).

## Layout and responsibilities

- src: source; index.ts, browser.ts, and node.ts define public entries.
- tests: meaningful behavior, boundary, and error checks.
- docs: English guides and API references; docs/zh-CN: Chinese counterparts. Contributors and AI agents directly maintain all Markdown files, including both api/ directories.
- scripts/check-docs.mjs: read-only documentation validation.
- lib: JavaScript and .d.ts files generated by tsdown; do not hand-edit or commit them.

Write Chinese TSDoc / JSDoc for public APIs: purpose, arguments, defaults, results, errors, and examples. Keep identifiers and standard tags unchanged. Write English and Chinese Markdown API descriptions directly in their reference pages; there is no separate description mapping. Use source and built .d.ts files to review signatures. Supporting types and parent classes are not necessarily public exports.

Keep ESM, named exports, and sideEffects: false accurate. Avoid accessing DOM during module initialization. Keep Node built-ins out of the root entry. Do not add PURE annotations without checking their meaning.

## Documentation languages

English is the default: README.md, CONTRIBUTING.md, CHANGELOG.md, docs/_.md, and docs/api/_.md. Chinese counterparts use root *.zh-CN.md and docs/zh-CN/. Maintain reciprocal links and semantic alignment. llms.txt points to English by default and includes Chinese entry points. Existing runtime messages do not change when documentation is translated.

Use ts code fences for standalone executable examples with real public imports; the checker type-checks these blocks. Use typescript fences for declaration references or fragments that cannot run independently. The reviewer must verify reference accuracy; these fragments are not compiled as standalone examples.

## AI-assisted API changes

Follow [AGENTS.md](AGENTS.md). Documentation is part of every public API change, without a separate reminder:

1. Implement the API and public export when necessary, then write Chinese comments.
2. Directly update English and Chinese API references, including export tables, descriptions, signatures, overloads, and affected supporting types.
3. Update both module guides with behavior, defaults, errors, and examples. New modules also need both indexes and llms.txt entries. Update both READMEs when quick-start usage changes.
4. Update both changelogs and relevant tests.
5. Run `npm run format`, then lint, format checks, type checks, tests, and `npm run docs:check`. Review both languages for completeness and consistency.

AI authors the Markdown and translations. tsdown generates distributed types. The checker only validates documentation; it does not generate or translate it.

## GitHub changes

The repository is [DvShu/utilane](https://github.com/DvShu/utilane). Commit source, tests, all Markdown documentation, and lockfiles. Exclude node_modules, lib, logs, credentials, and .env. Keep package metadata aligned with the repository.

Describe behavior, compatibility impact, and validation in PRs. Update both changelogs for interface or format changes.

## npm release

1. Utilane starts as a standalone package at version 1.0.0. Choose later versions according to the actual changes.
2. Review both changelogs, READMEs, guides, and API references, then run the checks above.
3. Run `npm pack --dry-run`, then `npm pack` to inspect the actual archive.
4. Check all three JS entries, their .d.ts files, English and Chinese READMEs, and LICENSE. Detailed Markdown documentation remains in the repository.
5. A maintainer publishes with `npm publish` using the correct account, then creates a version tag and GitHub Release.

Prepack runs lint, formatting checks, type checks, tests (including a build), and the read-only documentation checker. Do not bypass checks with --ignore-scripts. Pack is local; publish releases the package. This project does not automatically push or publish.
